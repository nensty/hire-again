# Privacy and security review — 23 October 2026

**Decision: keep public publication paused. Do not relaunch the current third-party/guest publication model.** A useful, smaller opt-in directory is possible, but the current prototype is not ready for a privacy or security sign-off. A working database permission system and passing tests do not establish permission to publish someone’s information.

This is a source-code, local database-policy, dependency-advisory, and browser review by the implementation assistant. It is not an independent penetration test, legal opinion, live infrastructure audit, or guarantee of no harm. Earlier reassurance that spam was the main added risk was incomplete.

Professional names, roles and URLs are personal data. They are not automatically GDPR special-category data, but their context can still cause harm. Public availability does not remove the need to assess lawful use, transparency, minimization, accuracy and individuals’ rights. Consent is the recommended product approach here, not a claim that it is the only possible legal basis in every situation. For an EU launch, review the [official GDPR text](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng), especially Articles 5, 6, 13–14, 17, 21, 25 and 32, with qualified advice where needed. Direct access to European Commission guidance was blocked in this environment, so no live guidance quotation or legal compliance certification is claimed.

## What the protective patch does

- A deliberate code-level hold is active in every mode, including the development preview. It has no environment-variable bypass. Reopening requires a reviewed code change and database change.
- Public home, submission, success and renewal pages show a neutral pause notice; listing detail pages and metadata receive no public records.
- New profile, role, single-post and bulk-post actions are blocked before database access. Show/renew operations are blocked, including valid signed reminder links. Existing authorized hide/delete actions remain available.
- Public data functions return before consulting caches, fixture data or the database. Real-person fixtures are removed from the current source tree; retired migrations no longer seed them. Already-applied rows are not deleted by editing historical files.
- `202610230001_privacy_hold.sql` adds non-destructive restrictive policies to all three listing tables. Anonymous readers see no rows, authenticated users see only their own records, inserts are blocked, and updates cannot make records active. Existing active rows are marked hidden without deleting their data. Operators can still run retention cleanup; this is not an attempt to revoke trusted service credentials.
- Automatic reminder emails stop while authorized retention cleanup continues. Owner sign-in remains available for data management.
- Responses request `private, no-store` caching and no referrer disclosure. This cannot recall an older response or prevent provider security logs.
- Prior local production-test servers started by this assistant were stopped. This does not stop remote deployments.

## Evidence and limits

Completed checks: 85 unit/database/action tests, 5 privacy-hold browser tests, lint, TypeScript/build, and production smoke checks at 375px and 1440px. These are local checks, not a live privacy certification.

- Local tests: actual Postgres via PGlite exercises all migrations, anonymous and cross-user reads, denied inserts/republication, owner hide/delete, and ownerless records. Server-action tests check that direct calls cannot bypass the hold. Baseline feature tests explicitly mock the hold off to preserve regression coverage; they are not evidence that publication is enabled.
- Browser tests cover paused public/submission routes, public detail metadata, owner sign-in access, caching headers, accessibility and overflow. The previous discovery UI scenarios are archived as disabled specifications because the feature is deliberately not served during the hold.
- Existing foundations include owner authorization/RLS, server-only privileged keys, input/URL validation, React text escaping, signed/versioned reminder controls, and expiry independent of cron. These reduce specific technical risks; they do not supply subject consent or a removal operation.
- `pnpm audit --prod --json` reported zero known vulnerabilities in the production dependency snapshot during this review. This is an advisory lookup, not proof of vulnerability-free software.
- No production Supabase, Vercel or operator-contact credentials were available here. No live rows were inspected or deleted, no remote policies were changed, and no affected people were contacted. There is no determination of how many people viewed or copied the records, or whether a legal notification obligation exists. Assess those questions with the operator and appropriate privacy/security support.

## Owner-controlled containment steps

1. Restrict the GitHub repository’s visibility/access. The original raw file was accessible without authentication during review. Preserve any necessary evidence privately; coordinate history cleanup with collaborators and GitHub before a destructive rewrite. Making the repository private is not a guarantee that previous copies disappear.
2. Deploy the held revision and disable or restrict older deployments/previews that can still serve earlier data. Verify the actual public URL, profile URLs and generated metadata in a signed-out browser. Do not rely on the local preview or a Git push as proof of deployment.
3. If a Supabase project was connected, review and apply the pending privacy-hold migration (`supabase db push` for the correctly linked project). Test the direct API with the publishable key and a separate ordinary account: no anonymous/other-user records, no new inserts/republication, owner deletion works. Keep privileged keys server-only.
4. Privately review any already-published entries, permission records, reports, access evidence, old source/deployment copies and provider retention. Decide on subject communication and any formal notification duties based on actual facts and qualified advice; do not infer a credential compromise from this source-data exposure alone.
5. Configure an identified, monitored operator contact. Keep publication paused until an opt-in, exact-entry approval and prompt withdrawal process has been implemented and tested end to end, and the owner can maintain it.

There is no reopening date or automatic reactivation. Passing the local tests does not satisfy these operational and consent gates.
